# Emulator PC-01 Lviv — Оценка проекта и список улучшений

## Общая характеристика

Проект представляет собой эмулятор советского компьютера ПК-01 «Львов» (1980-е гг.), реализованный как Chrome Packaged App (manifest v2) на чистом JavaScript и HTML5. Ядро эмулятора — это процессор Intel 8080 (КР580ВМ80А), страничная память, I/O-порты (i8255A), видеовывод на `<canvas>`, звук через Web Audio API и клавиатура.

**Состояние проекта:** последний коммит — v1.1.0, проект стабилен, но не обновлялся, технологически устарел.

## 🔴 Критические проблемы

### 1. Chrome Apps deprecated

> [!CAUTION]
> Manifest V2 Chrome Packaged Apps **полностью удалены** из Chrome с 2024 года. Эмулятор невозможно запустить в современных версиях Chromium/Chrome.

**Рекомендация:** Миграция на веб-приложение. Ниже — сравнение вариантов.
> [!NOTE]
> **Статус:** Фаза 1 (SPA/Vite) успешно завершена. Приложение работает в современных браузерах.

#### Вариант A: SPA (Single Page Application на Vite)

| | |
|---|---|
| ✅ **Максимальная простота** | Достаточно обернуть код в Vite-проект |
| ✅ **Быстрый старт** | Можно начать без переписывания на модули |
| ✅ **HMR** | Удобство разработки с Hot Module Replacement |
| ✅ **Предсказуемость** | Нет проблем с кэшированием Service Worker |
| ❌ **Нет оффлайн** | Каждый раз нужен интернет |
| ❌ **Нет установки** | Нельзя поставить иконку на рабочий стол |
| ❌ **2+ МБ по сети** | Дампы скачиваются при каждом визите |

#### Вариант B: PWA (Progressive Web App)

| | |
|---|---|
| ✅ **Оффлайн-работа** | Service Worker кэширует все ресурсы — критично для эмулятора |
| ✅ **Установка** | Иконка + окно без адресной строки — ближе всего к Chrome App |
| ✅ **Нулевой порог входа** | Достаточно перейти по URL |
| ✅ **Кроссплатформенность** | Десктоп, мобильный, планшет |
| ✅ **File System Access API** | Современный аналог `chrome.fileSystem` (Chromium) |
| ❌ **Ограничения Safari/Firefox** | File System Access API не поддерживается, нужен fallback |
| ❌ **Горячие клавиши** | Ctrl+P/Ctrl+S перехватываются браузером |
| ❌ **Сложность** | Service Worker + манифест + стратегии кэширования |

### 9. Повторяющийся код проверки типов

Конструкторы всех классов дублируют один и тот же паттерн:

```js
    throw new Error('...: Invalid CONFIG object');

```

Нет типизации, нет единообразного подхода к валидации.

### 10. Неоптимальная конвертация в grayscale (`screen.js`)

```js
// screen.js:221 — используется && вместо побитового умножения
sum = ((p & 0x00FF0000) && 0x1D) + ((p & 0x0000FF00) && 0x96) + ((p & 0x0000FF) && 0x4C);
```

Оператор `&&` выполняет логическую проверку, a не побитовое умножение. Если любой канал ≠ 0, результат — константа (0x1D, 0x96 или 0x4C), что **некорректно**. Для полутонов нужно:
```js
sum = ((p >> 16) & 0xFF) * 0.114 + ((p >> 8) & 0xFF) * 0.587 + (p & 0xFF) * 0.299;
```

> [!NOTE]
> **Уточнение:** После тестирования выяснилось, что использование `&&` вместо умножения — это НЕ ошибка, а особенность эмуляции. Такая логика даёт более яркое изображение, похожее на реальный ч/б телевизор PC-01. Исправление на правильное умножение делает изображение слишком тёмным. Код оставлен как есть с поясняющим комментарием.

### 11. Непоследовательное управление памятью в `terminate()`

```js
// profile.js:251
'settings,config,beeper,...'.split(',').forEach(function(prop) {
    this[prop] = null;
}, this);
```

Необычный паттерн — строка со списком свойств, разбиваемая `split`. Непрочитаемый и хрупкий код.

### 12. `store_flags()` — избыточные операции

```js
// i8080.js:117-143
var f = 0;
if (this.sf) f |= F_NEG;
else f &= ~F_NEG;  // f = 0, &= ~0x80 = ничего не делает
```

Ветки `else` бесполезны, т.к. `f` начинается с `0` — обнуление и так даёт `0`.

### 19. Неполная дешифрация банков памяти (`memory.js:263`)

```js
if ((mem_map === 144 || mem_map === 256) && (io.EXTENDED_MODE_PORT & 0x04)) {
```

Здесь проверяется `io.EXTENDED_MODE_PORT` (константа `0xF0`) побитово с `0x04` — `0xF0 & 0x04 = 0`, поэтому **ветка никогда не выполнится**. Вероятно, должно быть `io.ports[io.EXTENDED_MODE_PORT]`.

### 22. Выделение бинарных данных в файлы

ROM-образы и дампы вынести из JS в `.bin`-файлы (или base64-encoded), загружаемые через `fetch()` / `import()`. Это ускорит парсинг JS и уменьшит потребление RAM.

> **Исправлено:** Настроены `package.json`, ESLint (Flat Config) и Prettier. CI/CD пока отсутствует.

### 24. TypeScript или JSDoc-типизация

Добавить типы (хотя бы JSDoc) для улучшения поддержки в IDE и предотвращения runtime-ошибок.

### 25. Web Worker для CPU-эмуляции

Перенести выполнение `I8080.run()` в Web Worker, чтобы основной поток не блокировался при тяжёлых вычислениях. Это улучшит отзывчивость UI.

### 26. `requestAnimationFrame`-based game loop

Текущий game loop (`setTimeout` → interrupt → `requestAnimationFrame` → `setTimeout`) сложен и нестабилен. Лучше построить цикл на основе единого `requestAnimationFrame` с фиксированным шагом (`fixed timestep`) и динамическим количеством CPU-циклов за кадр.

### 27. Отделение UI от логики

Эмулятор тесно связан с DOM (через `Setting`, `Viewport`, `Keyboard`). Выделить логику эмуляции в чистые модули без DOM-зависимостей — это упростит тестирование и переносимость.
